# Telegram: кандидаты покупки по шести условиям

## Что добавлено

На страницах анализа акции и обзора — панель «Telegram · кандидаты покупки».
Она использует **TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID того же бота, что у радара**.
Отдельного бота и OpenAI API не нужно. Секреты не передаются в браузер и не пишутся в журнал уведомлений.
Наличие настроек проверено локально, их содержимое не выводилось. Реальная доставка на этом этапе не проверялась: все тестовые отправки подменены.

Настройки по умолчанию выключены. Указать тикеры через запятую или с новой строки,
включить «Присылать кандидатов» и сохранить. Лимит списка в 5 акций убран.
Этот серверный список отдельный от списка обзора в localStorage. Настройки и защита от повторов
хранятся в игнорируемом Git файле `data/telegram.sqlite3`.

## Что приходит

Тикер, совпадение 6/6 исходных условий, цена лучшего предложения по снимку, стоп/цель существующего сценария,
время биржевого снимка и предупреждение о риске. Это **экспериментальный кандидат правил**, не одобренный
нейросетью вход, не вероятность заработка и не обещание роста. Нейросети и их запреты не изменены;
их наблюдения WATCH сами по себе никогда не запускают Telegram. Торговые заявки не выставляются.
Шорт и уведомления о продаже не добавлены.

Отправка допускается только для свежего live LONG без blockers, со всеми шестью true-условиями,
планом `0 < stop < entry < target`, обычной торговой сессией и подтверждённым качеством
`stream_exchange_v1`. Время анализа — не старше 25 секунд, стакана — 45 секунд; будущее время запрещено.
Источником остаётся существующий сервис, который отдельно проверяет свежесть свечей и ленты.
Демо, fallback без подтверждённого стакана, истёкшая оценка и ошибочный ответ не отправляются.

## Для работы

1. Сервер запущен, корректные `INVEST_TOKEN`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` загружены из своего `.env`
   или через `INVEST_ENV_FILE`. При смене переменных перезапустить сервер. При необходимости открыть бота и отправить `/start`.
2. Отдельный терминал из каталога с `manage.py`, то же виртуальное окружение и `.env`:

   ```powershell
   python manage.py watch_telegram --seconds 28800
   ```

   Сначала сохранить список на сайте: команда прочитает его из SQLite, без ограничения длины командной строки Windows.
   Старый `watch_market` перед запуском остановить через Ctrl+C: действует общая блокировка одного сборщика.
   Этот сборщик ограничен 8 часами и 1 ГБ по умолчанию. Без него нет проверенного живого стакана/ленты,
   вход остаётся заблокированным. При изменении списка нужен соответствующий перезапуск сборщика.
3. Включить уведомления в панели. При обычном `runserver` фоновая проверка запускается автоматически,
   включая восстановление после перезапуска. Вкладку можно закрыть; сервер и сборщик должны остаться работать.
   Сон, выключение компьютера, отсутствие связи или завершение срока сборщика прекращают полезное наблюдение.

Для WSGI/ASGI-развёртывания без `runserver` — отдельный процесс:

```powershell
python manage.py telegram_signals
```

Он читает те же сохранённые настройки. Альтернатива — посещение панели после каждого запуска сервера
запускает поток в текущем веб-процессе. При нескольких процессах один владелец определяется арендой SQLite;
это не системная служба и не гарантия круглосуточной доступности. Сборщик запускается отдельно.

## Расширение списка: не бесконечные одновременные подписки

- Ограничения в 5 тикеров, 80 символов поля и 4 КБ запроса сняты. Поле многострочное, повторы убираются.
  Остаётся защита HTTP-запроса 1 МиБ и обычные ограничения памяти/диска. Это не обещание буквально бесконечного списка.
- Новый `watch_telegram` собирает до 50 акций одновременно: стакан, ленту, закрытые 1м/15м свечи и статус.
  Это 200 учитываемых подписок. [Документация Т-Банка](https://developer.tbank.ru/invest/intro/intro/limits)
  указывает 300 подписок на один поток суммарно по стаканам/ленте/свечам; Info не учитывается.
  Ограничения брокера не отключаются и не обходятся.
- Список длиннее 50 разбит на группы с ротацией раз в 15 минут. Пример 123 акций: группы 50/50/23,
  полный цикл около 45 минут, если нет сетевых задержек. Вне активной группы нет текущего сигнала.
  Время разрешения инструментов, переподключения, прогрев и очередь могут увеличить реальную задержку.
  Длинный список может не успеть пройти целиком за ограниченные 8 часов сеанса; покрытие видно на сайте.
- Сам анализ — справедливая очередь до 3 акций одновременно. Следующие задания добавляются только после
  получения результата/таймаута предыдущих: большой список не переполняет кэш сигналов на 40 записей
  и не создаёт тысячи ожидающих заданий. Просроченный LONG не становится уведомлением.
- Включение бота не запускает сборщик автоматически. В панели видны число сохранённых тикеров,
  активное покрытие и номер группы. Вне группы/при остановленном сборщике карточка не показывает старую покупку
  как текущую. Карточки подгружаются по 50; контейнер прокручивается.
- Неизвестные акции TQBR пропускаются с явным статусом; остальные продолжают наблюдаться.
  Лимиты архива, 8 повторных ошибок, отмена RPC и отсутствие автоматического удаления сохранены.
- Прежние `watch_market`, `collect_microstructure`, `monitor_signals`, исследования и файлы моделей не изменялись.
  Новый широкий сборщик использует прежние формат данных/проверки и отдельную версию health `wide_watch_v1`.

Больше бумаг не гарантирует больше полезных сигналов или прибыль. Короткие движения между проверками
и вне текущей группы могут быть пропущены. Реальная пропускная способность большого списка на брокере
в этом изменении не измерялась; сетевые тесты подменены.

## Повторы и доставка

- Один сигнал на непрерывную серию LONG. Новый только после свежего подтверждённого WAIT/EXIT
  с хотя бы одним false-условием, и минимум через 30 минут с предыдущей попытки/отправки.
- Ошибка, пробел данных, demo или выключение/включение не сбрасывают серию.
- Попытка записывается **до** сети; параллельные вкладки/процессы не должны отправлять её повторно.
- Доставка отмечается подтверждённой только по `ok:true` и `message_id` Bot API.
  Это подтверждение принятия Telegram, не прочтения пользователем.
- При явном отказе — пауза от 60 секунд, для 429 учитывается `retry_after`, после паузы нужно заново
  получить свежий кандидат. Нет очереди старых сигналов для отправки позже.
- Таймаут/неясный ответ/авария после начала отправки: доставка неизвестна, автоматического повтора
  этой серии нет. Это сознательный выбор в пользу отсутствия дублей с риском пропустить сообщение.
  Гарантии exactly-once нет: у `sendMessage` здесь нет ключа идемпотентности.
- Выключение отменяет следующие проверки; уже начатый сетевой запрос может завершиться.
- HTTPS проверяется штатно, перенаправления запрещены, ожидание ограничено 8 секундами,
  тексты исключений/URL с токеном не выводятся. API настроек только localhost, изменение через POST+CSRF.

Реализация транспорта сверена с [официальным Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).
Существующие режимы бота радара не включаются и не выключаются этой панелью.

## Проверки

Первоначальные проверки: 25 Python-тестов и 5 JavaScript-тестов — fresh/live gate, модель не заменяется, demo/stale/сессия/качество,
план/NaN/мелкие цены, постоянная дедупликация и cooldown, гонка потоков, аренда worker,
явный отказ/429/неясная доставка, POST+CSRF+localhost, отсутствие секретов и HTML-инъекций в UI.
Полный прогон: **629 Python-тестов и 36 JavaScript-тестов прошли**, Django system check и `git diff --check`
без ошибок. В браузере проверены сохранение выключенных настроек с CSRF и ширины 390/1024 px —
горизонтального переполнения новой формы нет. Уведомления оставлены выключенными, тестовых реальных
сообщений не отправляли. Это тесты программы, **не доказательство прибыльности**.

Расширение списка дополнительно проверено на 123/500/1000/10000 синтетических тикерах: полное разбиение,
переход между группами, отсутствие голодания хвоста очереди, максимум 3 задания, таймауты,
200 подписок на группу, полный список в SQLite-архиве, неизвестные тикеры и лимиты диска,
сохранение большого JSON через POST+CSRF и порционная отрисовка. Старый тест проверки изменённого
файла ИИ один раз упал при немедленной перезаписи временного файла того же размера: Windows сохранил
тот же mtime. В тесте явно изменена метка времени временного файла; рабочий загрузчик/модель не менялись.
Окончательный полный прогон: **645 Python-тестов и 39 JavaScript-тестов прошли**; Django check и
`git diff --check` без ошибок. В браузере сохранены 8 акций при выключенных уведомлениях, проверены
ширины 390/1024 px без горизонтального переполнения; после проверки восстановлен исходный список SBER
и выключенное состояние. Сборщик на реальном широком списке не запускался, сообщений Telegram не отправляли.
