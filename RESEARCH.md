# Vorby Pro: исследовательский терминал

## Что реализовано

- `/` — разбор одной акции, свечной график, EMA 50, приближённый VWAP, стакан, шесть объяснимых условий покупки, предупреждение о возможном выходе из уже купленной акции и условный сценарий входа/стопа/цели.
- `/watchlist/` — список до 20 тикеров, сохранение в этом браузере, независимый статус каждого инструмента.
- `/terminal/` — прежний терминал; прежние портфель и API оставлены.
- `/api/signals/`, `/api/research/`, `/api/forward/`, `/api/paper/` и `/api/risk/` — GET API; не размещают торговых заявок и не вызывают Telegram.
- Отдельный учебный режим с явно вымышленными ценами. Он не включается вместо недоступных котировок автоматически.

Это лимит *планового* убытка, не гарантия: при ценовом разрыве фактический выход может оказаться хуже стопа.

Добавлен журнал условных сделок по сохранённым живым снимкам стакана. План при `LONG` фиксируется вместе с версией правил; вход допускается только по следующей свежей котировке в течение 90 секунд. Выход — по стопу, цели, предупреждению `EXIT` или через 180 минут. Если наблюдения прервались более чем на 90 секунд, исход остаётся неподтверждённым, а доходность не додумывается. Компактные наблюдения для журнала хранятся до 180 дней; ранее записанные снимки без зафиксированного плана не превращаются задним числом в сделки. Журнал начнёт давать результаты только после появления **новых** кандидатов покупки и последующих котировок. Это не настоящие сделки.

Историческая проверка теперь показывает четыре последовательных периода и итог с удвоенными расходами. Для семи уже сохранённых наборов по 180 дней (SBER, GAZP, LKOH, NVTK, GMKN, ROSN, YDEX) перепроверены пять свечных вариантов при комиссии и проскальзывании по 0,05% за сторону: **все 35 сочетаний оказались убыточны, у каждого — 0 прибыльных периодов из 4**. Например, на SBER суммарный результат четырёх периодов составил −79,0% для EMA 50, −59,6% для «тренд + VWAP + объём» и −28,9% для редкого входа по тем же трём условиям. Это другая нарезка уже просмотренной истории, поэтому цифры не сопоставимы напрямую с таблицей последних 30% ниже и не являются новой независимой проверкой. Полные правила с лентой и стаканом этим свечным тестом **не** проверены. Оснований обещать доходность или советовать реальные покупки пока нет.

Проверено 68 автоматических тестов и `manage.py check` без ошибок. В частности, тесты охватывают лотность, расходы, датировку свечей, разделение периодов, вход по следующему снимку и пропуски котировок. Для длительного сбора наблюдений во время торгов можно запускать `python manage.py monitor_signals --tickers SBER GAZP LKOH --interval 30` в отдельном терминале; процесс надо оставить работающим.

## Как читать сигнал

LONG означает только совпадение всех шести правил на свежих данных при подтверждённом статусе обычных торгов:

| Условие | Правило первой версии |
|---|---|
| Тренд | Последнее закрытие 15 минут выше растущей EMA 50; прогрев 100 свечей |
| Сделки | Покупки-инициаторы составляют минимум 58% объёма направленных сделок за 5 минут; минимум 5 сделок |
| Объём | Объём последней закрытой 15-минутки минимум 1,3 среднего предыдущих 20 |
| VWAP | Два минутных закрытия и текущая середина стакана выше приближённого VWAP дня |
| Спред | Разрыв лучшей покупки и продажи не больше 0,10% |
| Стакан | В общей полосе ±0,2% от текущей цены осталось минимум 65% прежнего максимума объёма покупок; минимум 3 снимка за 45 секунд |

Веса 20/20/15/20/15/10 — **баллы выполнения правил покупки, не вероятность прибыли**. При этой строгой версии кандидат покупки требует 100 баллов, но даже 100 баллов не разрешают сигнал при устаревших данных или закрытых торгах. «Проверь продажу» (в коде `EXIT`) — отдельное предупреждение **только для уже открытой длинной позиции**: закрытие 15-минутной свечи ниже падающей EMA 50, доля покупок в последних сделках не выше 42%, а два минутных закрытия и середина стакана ниже VWAP. Требуются свежие данные и подтверждённая обычная торговая сессия. Это не команда открыть короткую позицию; если акция не куплена, смысл сигнала — воздержаться от покупки. При остальных ситуациях — «Ждать» (`WAIT`). Пороговые значения — исходные гипотезы, не найденные прибыльные параметры.

Покупки и продажи здесь означают сторону инициатора, а не количество покупателей против продавцов. У любой сделки есть обе стороны. По агрегированному стакану нельзя узнать личность трейдера либо надёжно отличить снятие заявки от исполнения. Проверка раз в ~30 секунд не обнаруживает все события внутри секунды и не является детектором спуфинга. Новости и сделки конкретных трейдеров эта версия не анализирует.

VWAP — приближение HLC3×объём по свечам, сброс в полночь Москвы; в графике используются 15-минутные свечи, в живом правиле — минутные. Сезонность объёма по времени дня не учтена. При открытии торгов минутных данных/снимков может ещё не хватать.

## Какие алгоритмы сравниваются

1. Тренд EMA 50.
2. Тренд + VWAP + повышенный объём.
3. Пробой максимума предыдущих 20 свечей + повышенный объём.
4. «Тренд + VWAP + объём» только при новом появлении условий и не чаще одного входа в день.
5. То же редкое подтверждение, но с возможным удержанием до 32 свечей.

В тесте: 100 свечей прогрева, затем хронологическое разделение 70/30, вход только на следующем открытии. Стоп — максимум из 1,5 среднего истинного диапазона последних 14 свечей и 0,3% входа; цель — два расстояния до стопа. Выход также после 12 свечей включительно с входной, кроме пятого варианта (32 свечи); возможен перенос через ночь. Если свеча задела и стоп, и цель, выбран худший вариант — стоп. Комиссия и проскальзывание начисляются на обе стороны. Позиция условно равна 100% капитала без плеча: это сравнительная модель, не совет по размеру позиции. Лотность, налоги, дивиденды, доступность исполнения и корпоративные события не моделируются. Просадка считается по закрытиям и может недооценивать внутрисвечную просадку.

Параметры не оптимизируются. Сравнение включает «купить и держать» на том же проверочном участке и отсутствие сделок (0%). Последние 30% — отдельный участок, но многократный подбор по нему уничтожит независимость проверки. 30 сделок — лишь предупреждающий минимальный ориентир, не статистическое доказательство.

**Полный шестикомпонентный алгоритм и предупреждение `EXIT` этим свечным тестом не проверены.** Для них нужна история стакана и ленты, собираемая во времени. Снимки живого режима сохраняются локально в `data/market.sqlite3`, хранятся 30 дней; учебные данные туда не попадают. Ниже описана новая проверка будущих котировок по такому архиву. Она лишь начинает собирать доказательства и не повторяет реальные сделки.

## Проверка живых оценок спустя час

Страница акции показывает накопленные результаты `/api/forward/?ticker=SBER`. В архив записываются свежие оценки с нормальным статусом торгов; старые записи без отметки пригодности исключаются. Для сравнения баллов выбирается первое пригодное наблюдение каждого московского часа. Кандидат покупки и предупреждение о продаже дополнительно фиксируются в момент **появления состояния**, даже если это произошло позже первого наблюдения часа. Повторяющиеся одинаковые сигналы подряд не считаются новыми событиями.

Берётся первая действительно записанная котировка через 60–70 минут после исходной. Если её нет, исход остаётся непроверенным — цена не достраивается из будущих свечей. Для условной покупки используется лучшая продажа на входе и лучшая покупка на выходе; комиссия и проскальзывание по 0,05% начисляются на обе стороны. Для предупреждения `EXIT` показывается изменение середины стакана за час: снижение цены соответствует смыслу предупреждения. Это короткий горизонт для проверки направления, а не расчёт реального результата владения акцией.

Показатели зависят от того, когда собирались наблюдения. Часовые сравнения могут быть связаны между собой, история хранится только 30 дней, а текущие пороги были придуманы до этой проверки. Нужны десятки **новых** появлений сигналов на разных акциях и в разных рыночных условиях, прежде чем судить об их пользе. Прежний журнал за 26 сентября содержал 464 записи и ни одного `LONG` или `EXIT`; он не доказывает эффективность полного алгоритма.

Чтобы собирать данные без открытой вкладки, в отдельном терминале из каталога `manage.py` можно запустить:

```powershell
python manage.py monitor_signals --tickers SBER GAZP LKOH --interval 30
```

Команда использует тот же `INVEST_TOKEN` или `INVEST_ENV_FILE`, опрашивает до пяти акций с интервалом 30–40 секунд во время торгов и записывает только локальные наблюдения. Когда все проверенные инструменты не торгуются, интервал увеличивается до пяти минут; при полной ошибке связи — до минуты. Она работает, пока открыт этот терминал; остановка — `Ctrl+C`. Для однократной проверки подключения есть `--once`. Если одновременно открыта страница того же тикера, оба процесса обращаются к API Т-Банка и расходуют его лимит запросов. При ошибке связи оценка не выдумывается. Команда не отправляет заявки.

Комиссия 0,05% и проскальзывание 0,05% **за каждую сторону**, условный капитал полностью в одной позиции, без плеча. Значения ниже — результат последних 30% после прогрева, не всей истории.

|---|---:|---:|---:|---:|---:|
| SBER | 13 427 | −41,81% / 250 сделок | −26,45% / 141 | −15,64% / 78 | −1,50% |
| GAZP | 13 410 | −51,97% / 313 | −38,43% / 188 | −21,57% / 93 | +5,57% |

**Вывод по исходным трём стратегиям: при этих правилах и расходах ни одна на проверенном участке не показала преимущества.** Выборка проверочного участка уже содержит 78–316 сделок. Фильтры сокращают число сделок, но в данном тесте не создают прибыль. Нельзя рекомендовать этот прототип как готовую прибыльную торговую систему. Число инструментов всё ещё ограничено. Полный алгоритм со стаканом и лентой требует отдельной будущей проверки и тоже не имеет доказанной доходности.

### Проверка двух вариантов с редкими входами

После результата на SBER/GAZP/LKOH добавлены заранее определённые ограничения: вход только при новом появлении тройного условия и максимум один вход в день по московской дате. Первый вариант закрывается не позднее 12-й свечи, второй — не позднее 32-й. Стоп, цель и расходы не менялись. В этом тесте комиссия 0,05% и проскальзывание 0,05% взяты **за каждую сторону**. Итог не учитывает налоги, дивиденды и реальные ограничения исполнения.

Машинные отчёты с исходными свечами (локально, вне Git): `data/research-20260926-132503.json` — первые три акции; `data/research-20260926-132614.json` — NVTK и GMKN; `data/research-20260926-133416.json` — ROSN и YDEX. Отчёты позволяют пересчитать результаты без повторного запроса к брокеру. Живые «Кандидат покупки» и «Проверь продажу» — **отдельные, ещё не протестированные** эвристики по свечам, сделкам и стакану; результаты этой таблицы нельзя переносить на них.

Проверка чувствительности на тех же свечах:

- без комиссии и проскальзывания «тренд + VWAP + объём» дал SBER +0,21% и LKOH +1,69%, но GAZP −6,79%; для LKOH это намного хуже простого удержания (+16,40%);

- комиссия 0,05% плюс проскальзывание 0,05% за сторону: основной результат в таблице.

Это указывает на слишком большой оборот: слабый валовый эффект не выдерживает даже комиссии. Проверка с ограничением частоты входов сократила потери, но не дала положительного результата. Теперь сайт начинает заранее заданную проверку живых оценок на будущих котировках. Дальше нужно накопить достаточно появлений сигналов на нескольких инструментах и оценить их без подбора по уже просмотренным результатам. До этого не использовать сайт как основание для автоматической покупки или продажи.

Исходные свечи и полные машинные отчёты сохранены локально и не включаются в Git. Основной: `data/research-20260926-110853.json`; без расходов: `data/research-20260926-111052.json`; только с комиссией: `data/research-20260926-111141.json`. Повторяемая команда:

```powershell
python manage.py research_signals --tickers SBER GAZP LKOH --days 180 --fee 5 --slip 5
```

Здесь расходы указаны в базисных пунктах: 5 = 0,05%. Команда сохраняет новый датированный JSON с исходными свечами, сделками и кривыми капитала. Повторить расчёт на тех же свечах без нового запроса к брокеру можно через `--input data/имя-отчёта.json`. Команда не оптимизирует параметры и не размещает заявок.

## Основания и ограничения идеи

Исследование [Cont, Kukanov, Stoikov: The Price Impact of Order Book Events](https://arxiv.org/abs/1011.6402) объясняет связь дисбаланса потока заявок с краткосрочными изменениями цены на исследованных американских акциях. Это не доказательство заработка на MOEX после издержек. Текущий фильтр снимков — упрощённая эвристика, не реализация OFI из статьи.

[The Probability of Backtest Overfitting](https://arxiv.org/abs/1408.1159) — причина не выбирать «лучший» набор параметров по одному красивому тесту. Следующая проверка потребует более длинной истории, нескольких инструментов и периодов, реалистичных расходов и наблюдения без реальных денег.

Источники API: [Python SDK Т-Банка](https://developer.tbank.ru/invest/sdk/python_sdk/faq_python), [рыночные данные](https://developer.tbank.ru/invest/services/quotes/marketdata), [последние сделки](https://developer.tbank.ru/invest/api/market-data-service-get-last-trades). Последние сделки не заменяют многомесячную историческую ленту.

## Запуск

Из каталога, где лежит `manage.py`, в Python 3.12+ с зависимостями `requirements.txt`:

```powershell
python manage.py runserver 127.0.0.1:8000
```

В `.env` рядом с `manage.py` нужен `INVEST_TOKEN` (предпочтительно read-only). Пример без секрета — `.env.example`. Вместо копирования токена можно указать `INVEST_ENV_FILE` — путь к существующему `.env`. После смены токена сервер нужно перезапустить. `.env`, архив наблюдений и виртуальное окружение не загружаются в Git.

На компьютере Андрея при проверке использовались существующие Python и `.env` из PyCharm, но **код запущен из этой копии репозитория**, не из старой папки PyCharm:

```powershell
$env:INVEST_ENV_FILE='C:\Users\Андрей\PycharmProjects\T-invest\core\.env'
& 'C:\Users\Андрей\PycharmProjects\T-invest\.venv\Scripts\python.exe' manage.py runserver 127.0.0.1:8000 --noreload
```

Запускайте эту команду из `C:\Users\Андрей\OneDrive\Документы\ChatGPT\Инвест Про\T-invest`. Пути к окружению индивидуальны для компьютера; на ноутбуке используйте своё окружение и конфигурацию.

Тесты:

```powershell
python manage.py test dashboard.test_signals
```

Обновления и накопление снимков в браузере работают, пока открыта и видима страница. Для независимого сбора есть команда `monitor_signals` выше; она сама не запускается вместе с сайтом. Первый запрос истории может занимать время, веб-страница при этом не блокируется. Пул — 3 запроса обработки инструментов одновременно, кэш ограничен. Это локальный исследовательский прототип; Django development server и DEBUG не предназначены для публичного размещения.
